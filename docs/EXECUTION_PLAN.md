# خطة التنفيذ العملية — خطوة بخطوة
### FitFlow v2 — AI-Powered Health & Rehabilitation Platform

> المرجع العلمي/المعماري: [`docs/PROJECT_PLAN.md`](./PROJECT_PLAN.md)
> هذه الوثيقة هي **ترتيب التنفيذ**: إيه اللي نعمله، وبأي ترتيب، وإمتى نعتبر الخطوة "خلصت".

كل خطوة لها رقم ثابت (مثال: `2.3`). عشان نبدأ شغل، تقول: **"نفّذ خطوة 2.3"**.

---

## الجزء الأول: فلسفة التنفيذ — إزاي نضمن "بدون أخطاء"

مفيش مشروع بيتبني من غير أخطاء، لكن في طريقة شغل بتخلّي الأخطاء **تتكشف بدري ورخيصة** بدل ما تتكشف بعد الإطلاق وغالية. القواعد السبعة دي إلزامية في كل خطوة:

| # | القاعدة | ليه |
|---|---------|-----|
| 1 | **شريحة رأسية (Vertical Slice)** — كل خطوة تنتهي بحاجة **شغالة فعليًا** من الـ DB للـ API للواجهة | يمنع اكتشاف أن الطبقات مش متوافقة بعد شهرين |
| 2 | **Contract-First** — نعرّف الـ Pydantic schema والـ API contract **قبل** كتابة المنطق | الفرونت والباك يتبنوا على نفس العقد |
| 3 | **Types من طرف لطرف** — `mypy --strict` في الباك + `TypeScript strict` + توليد types للفرونت من OpenAPI تلقائيًا | يقتل فئة كاملة من أخطاء التكامل (اسم حقل غلط، نوع غلط) |
| 4 | **Rule Engine = دوال نقية + Golden Tests** — كل قاعدة علمية لها حالات اختبار مرجعية محسوبة يدويًا ومراجَعة من أخصائي | ده قلب المشروع؛ خطأ هنا = خطر على مريض |
| 5 | **لا merge بدون CI أخضر** — lint + types + tests + build | يمنع "الكود شغال عندي" |
| 6 | **كل Migration قابلة للتراجع ومختبَرة** (`upgrade` ثم `downgrade` ثم `upgrade` على نسخة) | يمنع كارثة على قاعدة بيانات فيها بيانات مرضى |
| 7 | **تكافؤ البيئات (Environment Parity)** — نفس Docker محليًا وعلى Staging وعلى Production | يمنع مفاجآت النشر |

**قاعدة ذهبية إضافية:** أي شيء يمس بيانات طبية (خطة تأهيل، تمرين، توصية) يمر عبر **Approval Workflow** ويُسجَّل في **Audit Log**. مفيش استثناءات.

## الجزء الثاني: قرارات لازم تتحسم قبل أول سطر كود

هذه القرارات لو اتأجلت، هنعيد شغل كتير لاحقًا.

### القرار 1 — الـ Stack: Self-hosted ولا Supabase؟

| | Self-hosted (Postgres + FastAPI Auth) | Supabase |
|---|---|---|
| سرعة البداية | أبطأ ~أسبوع | أسرع |
| التحكم في البيانات الطبية | كامل | مقيّد بالمزوّد |
| Audit Log + RBAC معقد | سهل ومباشر | يحتاج التفاف (RLS policies) |
| مصدر هوية واحد | نعم | اتنين (Supabase Auth + بياناتك) |
| النشر على DigitalOcean/Coolify | طبيعي | يحتاج ربط خارجي |

**التوصية: Self-hosted.** المكسب من Supabase (توفير ~أسبوع في الـ Auth والـ Storage) لا يوازن التعقيد اللي هيدخل بسبب أن المشروع ده محوره **صلاحيات معقدة + سجل تدقيق + Approval Workflow على بيانات صحية**. ومعاك خبرة DigitalOcean بالفعل.

### القرار 2 — نطاق الـ MVP الأول

**التوصية:** MVP = **مسار التغذية كامل** (تسجيل → ملف شخصي → Rule Engine غذائي → شرح بالـ AI → اعتماد الأخصائي → متابعة يومية). التأهيل يجي بعده.
**السبب:** التغذية منطقها أوضح وقابل للتحقق رياضيًا، والتأهيل يحتاج محتوى علمي مراجَع من أخصائي (ده أطول جزء زمنيًا وممكن يشتغل بالتوازي).

### القرار 3 — اللغة والاتجاه

عربي **RTL** أساسي، وإنجليزي ثانوي. يتحدد من اليوم الأول (`next-intl` + Tailwind RTL) لأن تحويل مشروع LTR لـ RTL لاحقًا مؤلم جدًا.

### القرار 4 — الريبو

نبني داخل `iMohamedMamdouh/FitFlow_v2` بهيكل monorepo (`backend/` + `frontend/` + `docs/`).

## 🟦 المرحلة 4 — محرك القواعد ⭐ (أسبوع 5-7) — أهم مرحلة

الهدف: منطق علمي **نقي**، بدون FastAPI وبدون قاعدة بيانات — دوال تاخد dataclasses وترجع dataclasses. ده اللي يخلّيه قابل للاختبار 100%.

| # | الخطوة | المخرجات |
|---|--------|----------|
| **4.1** | نماذج المدخلات/المخرجات | dataclasses نقية (`ProfileInput`, `InjuryInput`, `PlanOutput`) — بدون ORM |
| **4.2** | `priority.py` | قرار الأولوية: `REHAB_ONLY` / `REHAB_PLUS_DIET` / `WEIGHT_LOSS` / `FITNESS` |
| **4.3** | `nutrition.py` — الحسابات | BMR (Mifflin-St Jeor)، TDEE، العجز/الفائض الآمن، حدود دنيا للسعرات (حماية) |
| **4.4** | `nutrition.py` — توزيع الماكروز | بروتين/كارب/دهون حسب الهدف والإصابة (بروتين أعلى في التأهيل) |
| **4.5** | `nutrition.py` — مولّد الوجبات | خوارزمية توزيع من **الأطعمة المختارة فقط** + استبعاد الحساسية |
| **4.6** | `rehab.py` | اختيار التمارين حسب مرحلة الإصابة + فلترة الـ contraindications + التدرج |
| **4.7** | `training.py` | برنامج لياقة للأصحاء (تقسيم أسبوعي، حجم، شدة) |
| **4.8** | `adjustments.py` | كشف الثبات (Plateau) + تقدم/تراجع الإصابة + حدود التعديل الآمنة |
| **4.9** | **حزمة Golden Tests** | ≥ 40 حالة مرجعية محسوبة يدويًا ومراجَعة من أخصائي، مخزّنة كـ YAML |
| **4.10** | ترقيم إصدار المحرك | `RULE_ENGINE_VERSION` يُختم على كل خطة مولَّدة |

**قواعد أمان إلزامية داخل المحرك (Safety Guards):**
- حد أدنى للسعرات: 1200 (إناث) / 1500 (ذكور) — لا يُتجاوز مهما كانت الحسابات
- أقصى عجز: 25% من TDEE
- إصابة `acute` → **يُمنع** توليد أي تمارين مقاومة على المنطقة المصابة
- أي مدخل خارج النطاق المنطقي → استثناء صريح، **لا قيمة افتراضية صامتة**

**DoD:** تغطية اختبارات ≥ 95% على `rule_engine/`، وكل Golden Test يمر، والمحرك لا يستورد أي شيء من FastAPI أو SQLAlchemy (يُفرض باختبار معماري).

**اختلافات مقصودة عن النص الأصلي:**

* **بدون shadcn/ui.** المكوّنات مكتوبة يدويًا بنفس الاصطلاح (`cva` + `cn`) — العدد المطلوب صغير، وإضافة مولّد مكوّنات كامل تكلفة صيانة بلا مقابل هنا.

* **لا نداءات API من المتصفح.** الجلسة في كوكي `httpOnly`، فكل قراءة في Server Component وكل كتابة في Server Action.

| **8.3** | شاشة مراجعة الخطة | ✅ اعتماد / طلب تعديل بسبب إلزامي / تفعيل، مع سجل الانتقالات |
| **8.4** | الملاحظات والتواصل | ✅ ملاحظات عامة وداخلية، مرتبطة بخطة اختياريًا |
| **8.5** | عرض سجل التدقيق للمريض | ✅ يشمل ما فُعِل على خطط المريض لا ما يحمل معرّفه فقط |

**مؤشرات القائمة (8.1)** مرتَّبة بالإلحاح لا بالأبجدية، ويُختار أعلاها لكل مريض:

| المؤشر | متى | لماذا في هذا الترتيب |
|--------|-----|----------------------|
| `needs_review` | خطة تنتظر توقيعه | الوحيد الذي يعطّله شخص آخر |
| `acute_injury` | إصابة حادة مسجَّلة | تُقدَّم على أي هدف (ADR-007) |
| `not_started` | ملف ناقص أو بلا موافقة | لا يمكن توليد خطة أصلًا |
| `stalled` | لا تسجيل يومي منذ 7 أيام | المتابعة انقطعت |
| `on_track` | لا شيء مما سبق | — |

**أُضيف في الباك اند:** `GET /specialist/patients` (بالمؤشرات)، و`/patients/{id}/profile` و`/logs` و`/notes` و`/audit`، وجسم طلب صحيح لإنشاء الملاحظات بدل تمرير النص في الرابط.

**استُكمل في المرحلة 10:** إسناد المريض للأخصائي كان يُنفَّذ بـ SQL يدوي، وصار شاشة في لوحة المدير.

**حارسان في مسار تعديل المستخدمين**، وكلاهما يمنع حالة لا رجعة منها:

| الحارس | لماذا |
|--------|-------|
| المدير لا يعطّل نفسه ولا يخفّض دوره | آخر مدير يفعلها يُغلق اللوحة على الجميع، ولا يوجد مسار عام لاستعادتها |
| الأخصائي ذو المرضى لا يُخفَّض دوره | قاعدة البيانات ترفضه أصلًا (مفتاح أجنبي مركّب على `users(id, role)`) لكن بخطأ سلامة غامض — والرسالة هنا تقول ما يجب فعله: انقل مرضاه أولًا |

التعطيل ليس ضمن الحارس الثاني عمدًا: تعطيل حساب مخترَق فعل عاجل، وعدد مرضاه ظاهر في الشاشة نفسها.

**أُضيف في الباك اند:** `GET/PATCH /admin/users` (بتصفية وبحث وأعداد الإسناد)، و`POST /admin/assignments`، و`DELETE /admin/assignments/{specialist}/{patient}` (إنهاء ناعم يبقي الصف وتاريخه)، و`GET /admin/stats`. الثلاثة الأخيرة مدقَّقة في سجل التدقيق.
